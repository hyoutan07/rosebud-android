## 通信の工夫と精度

- `SuctionTrack`が動作終了、150ms再送、300ms待機再送の期限を持つ。古い非同期終了タイマーは作らず、OFF/再ON/全停止で以前の期限を捨てる。
- 既存の単一actorの25ms監視で期限を扱う。0.05秒を100msへ丸めない。ただしOSのスケジュール誤差、各台のDeviceMessageTimingGap、前のScalarCmd応答待ちは実送信時刻へ加わる。**指令上の50msと物理的な50msは別**であり、後者は未測定。
- V/Fと吸引を合わせて各台1件だけScalarCmd応答待ちにし、通信間隔を共有。吸引の最新値をV/Fより先に送信機会へ載せる。待機中の0は約300msごとなので、常にV/Fを押しのけるものではない。Webの「吸引後100msはV/Fを破棄」はそのまま移植せず、既存のV/F生成を維持する。
- 応答が遅い台には過去のパルスをキューに積まない。終了した吸引の0が未確認の台は、次の非ゼロより0を先に送り、その応答を確認する。台ごとに管理し、片方の遅延で他方を止めない。
- 古い応答は停止世代を跨いで状態を復活させない。全停止は再送タイマーを消すだけでなく、既存のStopDeviceCmdで全系統を停止し、対象全台の応答を待つ。
- ScalarCmdのエラー/1500msを超える応答待ちは黙殺せず、既存の故障→全停止→Service終了へ進む。通信が届かない条件は停止未確認として残す。送れなかった非ゼロを後から再生しない。

## 停止・切替

| 経路 | 吸引の扱い |
| --- | --- |
| 吸引の自動OFF | 自動期限を解除、0＋150ms後の0。V/Fは継続。手動の非ゼロは新たな明示操作 |
| V/Fの一時停止 | 吸引autoも解除・0、StopDeviceCmdで3系統の停止応答を待つ。V/F再開でも吸引は自動再開しない |
| 吸引だけのpause要求 | 全対象停止、吸引解除。V/Fセッションのない状態を再開可能なセッションにしない |
| 全停止・通知停止・音声/Service終了 | 吸引解除、全対象停止・停止応答確認、音声・接続を終了 |
| 接続断・対象消失・エラー | 吸引解除。停止できた/未確認を区別し、自動再接続・自動再開なし |
| 対象/プレビュー/シナリオ切替 | 吸引ON、非ゼロ、または0の再送・応答確認中は変更をロック。0が落ち着いてから切替 |
| Flicker単発確認 | 吸引ON/非ゼロ中は開始不可。単発動作中の吸引操作も不可 |
