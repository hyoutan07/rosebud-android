# Handy：開始・段階切替の停止判定を外す

2026-10-22、0.14.7/code25。本人から位置読取りエラーの再発とBluetooth接続解除を報告。0.14.4の連続運転中の読取り復旧とは別に、開始/段階切替の停止判定が残っていた。

## 確認できたことと限界

取得したcontrolログの保持範囲は2026-10-21 22:59:28〜23:00:50 JST。最新Handy状態は位置26.6667mm、最終目標9.5121mm、経過823ms、未接続/停止応答未確認。画面でも未接続と同じ残存状態を確認した。これは確認時点のアプリ表示で、ユーザーが報告した実機の動作を否定するものではない。

保持範囲の先頭付近に「停止中の現在位置を取得できませんでした。再接続してください」、直後に「Handyとの接続が切れました」。この前のHandy情報はRosebud併用の大量の送信ログに押し出されており、今回最初の原因がこの判定だけだったとは断定できない。

コードでは段階切替のたびに715停止→prepare→最初の842で速度0.1mm/秒以下を要求。715の受理と物理停止完了は違うため、残速があるだけでfailしてシナリオを終了する経路があった。また、開始の二重到着がreadyの例外となり、すでに動くシナリオを終了する経路もあった。

## 変更

- 通常の段階切替は既存の連続軌道へ反映。停止指令・世代変更・開始前位置確認を挟まず、軌道の位置/速度の連続性と次の反転での設定反映を維持する。
- 開始時は715を確認後に位置と速度を再照会。残速・一時的な不正/古い値・範囲外の観測は、その1回で失敗終了せず約250ms後に確認し直す。状態が整えば開始する。確認中の全停止/切断は世代/停止トークンで未完了の開始を破棄する。
- 実行/開始準備中の重複開始は無視し、動作中のセッションを終了しない。
- 連続運転中の位置読取り復旧・保存範囲・速度制約・専用停止・実切断時の終了は維持。絶対に物理運動が途切れないとの保証はしない。
- transportの終了通知を受けてserviceがもう一度停止指令を送る再入を廃止。transportが所有する1回の停止/解放へ任せ、失敗通知の連鎖と、検索失敗なのに二重停止の未確認表示になる状態を避ける。
- GATT切断のstatus、新state、処理中RPC、transport/sessionどちらのエラーか、開始前の生位置/速度/準備状態を記録する。
- Handy専用のhandy.jsonl/handy.1.jsonl/handy.2.jsonlを各512KiB上限で追加。RosebudのログでHandyの前後関係が消えないようにし、診断書き出しにも含める。生音声は保存しない。

はじめ/中間/フィニッシュの速度・全幅頻度・予定休憩・音連動/乱数は[現行の体験仕様](handy-pacing.md)を維持する。担当の既知の利用上限によりメインが確定修正を継続する。
