# Handy：波形の連続追従と到達誤差の扱い

現行の速度・全幅・休憩と初期上限は[0.14.3の調整](handy-power-tuning.md)を参照。以下は0.14.2の導入履歴。

2026-10-21、0.14.2/code20。本人が0.14.1を確認し、端点で止まる機械的な往復ではなく、上下端・幅・速さが滑らかに揺らぐ波、大きな上下往復を増やすこと、通常の到達遅れで毎回再スタートさせないことを依頼。接続と画面は良いとの評価を維持する。

## 原因と変更

0.14.1は1区間ごとに目標位置±1mmかつ速度0を待って次を送った。そのため各端で通信・判定の間が入り、固定位置の往復にも見えた。ログでは目標43.189343mmに対し42.0mm・速度0の正常応答が続いていたが、約1.189mmの差で到達判定が通らず「移動の応答が遅れたため停止しました」となった。単純な通信タイムアウトとは別の誤停止。

シナリオはこの到達待ちから外し、時刻に対応する未来の目標をおよそ100ms間隔で更新する。1件のFirmware応答後に最新の点だけを採用し、過去の点の送信待ちを積まない。約250msごとに位置・速度を読み取り、現在の位置から各送信時間を制約する。目標との差や速度0への到達はシナリオ継続の条件にしない。

返信が遅れた場合も最新の時刻へ追従し直す。返信と読取りにかかった時間を基に200〜500msの先読みへ調整し、送信処理の間に早着しすぎることを抑える。速度上限を超える距離なら時間を延ばす。±1mmの判定を緩めただけ、期限を無限にしただけの修正にはしない。

## 波の生成

- 半往復ごとに上下端・幅・半周期を少し変える。乱数は区切りでだけ使い、毎回の更新に白色雑音を入れない。
- 位置は5次補間でつなぎ、反転時の速度・加速度を0へ滑らかに戻す。そこで待機せず次の半往復へつなぐ。数学的な滑らかさと実機の速度制限は区別する。
- 原則として10半往復中8半往復は広い範囲を使う。一部候補は常に広め。残りに上側・下側・小刻みの挿話を入れる。自動テストでは全13候補で大きな半往復の比率が60%を超え、上端・下端が固定値の繰り返しにならないことを確認する。
- 大きな波の上下端は範囲内約2〜13%／87〜98%を基準に毎回変える。短い挿話は中心・幅も変える。ユーザーの保存上限と機器の可動範囲の内側・両端1mm余白は維持する。
- 速度には独立した時間の波と区間ごとの穏やかな揺らぎを重ねる。導入は穏やか、中間は長期の加速に短い谷、フィニッシュは高速を基調にする。8/7/5分・13重み・20秒保持/80秒目安・音特徴・Handyだけの時計保留・段階ボタンは維持する。
- 時計の更新は波を進めたり乱数を消費したりしない。長い処理遅延では過去を無限に作らず、上限256区間で現在位置から新しい波へ戻す。

旧tickの区間生成は互換のため残すが、HandyServiceの通常シナリオはsampleTrajectory経路を使う。有限入力テストは入力した区間・予定時間・到達確認という別用途のまま。

## 継続と終了の境界

正常な位置応答が返り、数値と設定範囲を確認できている限り、通常の位置誤差や到達の遅れを理由にシナリオを中断しない。一方、実切断、不正応答、設定外の位置、4秒間位置更新がない場合、従来の3秒RPC期限や音声更新喪失など、機器の状態を確認できない場合の停止は残す。何が起きても無制限に送信し続ける仕様ではない。専用715・世代管理・全停止は維持する。

接続・スキャン・BLE権限・RPC形式は変更しない。各目標はstopOnTarget=trueのまま、更新が途切れた際もその目標で停止する指令にする。公式[HDSP仕様](https://www.handyfeeling.com/api/handy-rest/v2/docs/spec.yaml)はfalseを連続更新の平滑化向けに説明するが、最終目標後の行き過ぎと保存上限内停止は確認できていないため今回は採用しない。これはFW3 REST資料の説明で、FW4 BLE内部実装の保証ではない。FW4の公開SDKスキーマには同じtag3 boolがある。最小速度付近での微細な動き・物理的な滑らかさは実機で調整する。
