# Handy：位置読取りの復旧と導入の低速化

2026-10-21、0.14.4/code22。本人から0.14.3で位置確認エラー→Bluetooth切断→動作不能、導入が速すぎるとの報告。WS不通も相談されたが、本人が解決したため対象から外した。「Handyだけ弱める」と「動きを入力してテスト・共有」は使用しないとの追加指定で画面から削除。

## 観測と判断

端末ログ12:58:07 UTCで、接続中の中間シナリオから「Handyの位置を確認できませんでした。」へ移り、アプリが切断。後の接続も同じ位置確認で3回失敗した。該当経路は842応答の位置が取得範囲±0.1mmから出るだけでtransport.failを呼び、715を送りBLEを閉じていた。異常値そのものは旧版で記録しておらず、実切断が先だったとは言えない。最終の正常値は位置10.6667mm、速度287.23mm/秒、目標66.6962mm。

実測の位置分解能は約0.667mmで、0.1mmの照合はそれより狭い。これは原因候補で、旧版の生データがない以上「丸めだけが原因」と断定しない。

## 現行の復旧方針

- 位置照会842の不正/欠落/タイムアウトを、移動/停止指令や実BLE切断の失敗と分ける。読取り失敗でBLEを閉じない。書込み完了しないATT障害は引き続き通信障害として扱う。
- 読取り数値が機器/保存範囲から1.5mm以内だけ外れる場合、観測位置を範囲へ寄せて扱う（約2 encoder stepと丸めの余裕）。送信目標の範囲は広げず、従来の両端1mm余白を維持する。それ以上のずれ、不正値は使わない。
- 一時的な読取り不良では最後に確認済みの位置を最大4秒まで使い、約250ms間隔で再照会する。読取り失敗でこの4秒の鮮度は更新しない。
- 4秒を越えたら新しい移動指令を控える。最後のstopOnTarget=true目標で終わり、Bluetoothと実行中のシナリオ/時計を保持して再照会を続ける。正常な位置が戻ると最新時刻の波へ自動復帰し、開始の押し直しは不要。物理的に無休止で動く保証ではない。
- 開始前の読取り失敗も接続を維持して自動照会。実切断・移動/停止RPCの失敗、音声連動の入力喪失、利用者の停止は従来どおり終了する。実切断やアプリ終了後の自動運転は追加しない。
- 再試行は接続世代・停止トークンで打ち切り、停止/切断後に以前の読取りが運転を復活させない。異常読取りの生位置・速度・機器範囲、アプリ範囲をログに記録し再発を切り分ける。

導入の速度包絡は32〜40mm/秒へ低下。通常送信の時間もmin(機器の速度上限,その時点の包絡上限)から距離に応じて延長し、位置の遅れを取り返すために導入で速い移動を要求しない。最小速度以下の遅さを本体が実現する保証はない。中盤・終盤の速度/全幅往復・まとまった動作と休憩は[0.14.3](handy-power-tuning.md)を維持。

UIは不要な2入口を削除。有限入力テストと弱化の内部モデル/過去試験は互換のため残すが、通常画面からは呼ばない。吸引・Rosebud側制御は変更しない。

## 検証と次の確認

範囲端の観測ずれ・大きな範囲外/不正値の拒否・失敗読取りで信頼時刻が更新されないこと・正常値の復帰・導入の距離/時間速度上限を単体テストに追加する。実機で旧エラーを再現して復旧する試験は別途、本人の使用後に確認する。新しい動きを自動開始しない。

既存担当は利用上限に達しており、確定した追加修正をメインが継続。導入・検証の詳細は[検証記録](validation/2026-10-21-handy-recovery-0.14.4.json)。
